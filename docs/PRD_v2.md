## 一、产品愿景

cn-social-agent 是一个**面向中国市场的多平台社交媒体 AI Agent 管理平台**，定位为「内容创作 + 私域运营 + 舆情监控」的一体化超级后台，对标 Jasper + Buffer + Sprout Social 的中国本土化版本。

核心差异化：
- **全中文平台覆盖**：钉钉、飞书、企业微信、微信公众号、微博、小红书、抖音
- **AI Native**：从选题→生成→审核→发布全链路 AI 驱动
- **私域 + 舆情**：国内竞品少见的内容 + SCRM + 舆情三合一

### 目标客户画像（待评审确认）

| 客户类型 | 特征 | 核心需求 |
|---------|------|---------|
| MCN 机构 | 10-50人，管理大量账号 | 多平台发布、团队协作、舆情监控 |
| 企业市场部 | 内部团队，按席位付费 | 审批流、品牌语调、数据报表 |
| 内容创业者 | 1-5人，追求效率 | 快速生成、一稿多发、数据追踪 |
| 私域运营商 | 注重 SCRM 和客户运营 | 收件箱、标签管理、自动回复 |

**待评审决策**：当前阶段优先满足哪类客户？这决定功能优先级和定价策略。

## 五、需求清单

> **数据来源说明**：Phase 1 所有平台 adapter（SCRM 收件箱、舆情监控、内容追踪）均为 **mock adapter**，真实平台 API 接入时间线见各需求备注。演示和内测阶段使用模拟数据，不影响功能流程验证。

### 阶段 1（P0 — 3-4周，修正）

#### R-01：数据分析 BI 仪表盘
**现状**：analytics 页面是静态占位符，假数据
**需求**：
- 接入真实后端数据（基于已有 review/scheduler/inbox 数据聚合）
- 新增端点：
  - `GET /api/analytics/content-trend?range=7d|30d|90d` → 从 review 审核记录聚合每日生成/发布量
  - `GET /api/analytics/platform-distribution` → 从 review.platforms 字段聚合
  - `GET /api/analytics/engagement?range=7d` → Phase1 返回 mock 数据（真实数据等 R-04 平台 API 接入）
  - `GET /api/analytics/publish-calendar` → 从 scheduler 任务表聚合（先走 T-05 改造）
- 使用 Chart.js（CDN）绘制：折线图（趋势）、饼图（平台分布）、柱状图（互动）
- 筛选器：7天 / 30天 / 90天
- **技术约束**：后端数据模型依赖 `review.db` 的 `platforms` 字段记录，需确认该字段在现有工作流中是否被正确填充

**验收标准**：
- [ ] 仪表盘加载真实数据（非 demo fallback）
- [ ] 折线图展示7天/30天内容生成趋势（从 review 记录聚合）
- [ ] 平台分布饼图展示各平台占比
- [ ] 7天/30天/90天筛选器切换后图表刷新
- [ ] 后端 API 异常时显示错误信息，不回退到 demo 数据

**优先级**：P0 — 用户最直观感受产品价值的模块

---

#### R-02：内容日历（发布排期）
**现状**：发布管理只有列表，无日历视图；scheduler 无 filtered listing
**需求**：
- 新增「发布日历」Tab（发布管理页第二个视图）
- 月视图：格子中显示帖子标题缩写 + 平台图标，颜色区分状态（待发布=蓝/已发布=绿/失败=红）
- 点击日期格子：弹出当日所有待发布内容（支持拖拽到其他日期）
- 拖拽排期：前端 `dragstart/dragover/drop` 事件 → `PUT /api/scheduler/tasks/{id}` 更新 `run_at` 字段
- 点击帖子：展开详情（内容预览、目标平台、状态）+「删除」「立即发布」操作按钮
- 新建内容按钮：跳转内容生成模块
- 后端依赖：先完成 T-05（scheduler filtered listing）
- **注意**：scheduler 的 `run_at` 为 ISO 时间戳，需确认前端拖拽时区处理正确

**验收标准**：
- [ ] 月视图正确渲染当月所有发布计划（来自 scheduler 任务表）
- [ ] 点击日期可查看当天所有内容
- [ ] 内容可拖拽到其他日期重新排期（`PUT /api/scheduler/tasks/{id}`）
- [ ] 新建内容按钮跳转到内容生成模块
- [ ] 状态变更实时反映（日历刷新）

**优先级**：P0 — 竞品 Buffer/Hootsuite 的核心差异化

**需求**：

  - 预设角色：admin / 编辑 / 审核者 / 查看者

**验收标准**：
- [ ] 成员列表展示所有用户
- [ ] 可邀请新成员（生成邀请链接）
- [ ] 可设置用户角色（admin/编辑/审核者/查看者）

**优先级**：P0（修正后）— 鉴于 team 模块是死代码，工时等同重写，**建议移至阶段2**，阶段1聚焦 R-01+R-02

### 阶段 2（P1 — 1-2个月）

#### R-04：内容表现追踪（Post Analytics）
**现状**：内容生成后无后续数据追踪
**需求**：
- 帖子详情页新增「表现数据」Tab
- 展示指标：曝光量、点赞数、评论数、转发数、完播率
- 时间趋势：发布后7天/30天内的数据曲线
- 平台对比：同一内容在不同平台的互动对比
- 后端新增：`GET /api/posts/{post_id}/analytics`
- **数据来源优先级**：
  1. 微博企业版 API（最开放，先接）
  2. 微信公众号数据助手 API（需认证公众号）
  3. 抖音/小红书（蓝V或商务合作，后置）
  4. Phase1：返回 mock 数据，标注「数据来源：模拟」

**优先级**：P1

---

#### R-05：智能收件箱（SCRM 增强）
**现状**：收件箱仅展示消息列表；scrm FastAPI app 未挂载
**需求**：
- 消息分类：
  - 按**意图**分类：咨询/投诉/合作/售后（`scrm/` 的 `detect_intent()` 已实现）
  - 按**情感**分类：正面/中性/负面（`sentiment/` 已实现）
  - 按**紧急度**：高/中/低（AI 判定）
- 筛选器：按平台/分类/情感/日期范围
- 回复模板：预设常用回复模板，快捷插入
- 快捷回复：AI 生成 + 一键发送（`/scrm/ai/reply` 已实现）
- 后端：先实现 aiohttp handler 覆盖 scrm 核心端点；真实 FastAPI mount 作为优化
- **注意**：平台 adapter 全为 mock，Phase1 为演示模式，不影响功能流程验证

**优先级**：P1

#### R-06：站内通知中心
**现状**：只有 Toast，无通知沉淀；通知铃铛是空壳
**需求**：
- 修复 B-04：通知铃铛绑定点击事件 → 展开通知下拉面板或跳转通知列表页
- 通知类型：审核结果/发布结果/危机预警/系统通知
- 通知列表页：支持按类型/已读未读筛选
- 通知设置：各类型开关
- 实时推送：SSE（`/api/notifications/stream`）推送新通知；复用 `server.py` 中的 aiohttp 现有基础设施
- **技术选型**：SSE（简单，无需 WebSocket 升级）；备选 WebSocket（等并发量 > 100 再升级）
- 后端通知写入：审核通过/拒绝时写通知记录（review approve/reject handler 中补充）

**优先级**：P1

#### R-07：草稿版本历史
**现状**：生成内容后无持久化；`review/drafts.py`（内存）和 `review/db.py`（SQLite）两套并存
**需求**：
- **统一方案**（先做 T-01）：以 `DraftDB`（SQLite）作为 source of truth，废弃 `review/drafts.py` 内存版，统一字段定义
- 内容生成结果自动保存为草稿（`POST /api/drafts`，触发点：生成完成时）
- 草稿列表页：`GET /api/drafts` — 标题/平台/创建时间/状态
- 草稿详情页：展示内容；版本历史（最近5个版本，支持 Diff 对比）；版本回滚
- 自动保存：前端定时 `PUT /api/drafts/{id}`（每30秒）
- 提交审核：从草稿触发审核工作流（复用现有 `review/` 逻辑）
- **注意**：内容生成模块的「发送审核」按钮需改为先持久化草稿，再触发审核

**验收标准**：
- [ ] 每次生成内容自动创建草稿记录
- [ ] 草稿列表页展示所有草稿
- [ ] 支持版本历史查看和回滚
- [ ] 草稿可重新编辑后提交审核

**优先级**：P1

## 九、demo fallback 规则（设计约束）

为防止假数据掩盖真实 API 问题，制定以下规则：

```
规则 1：后端 API 存在但返回错误 → 显示真实错误信息，不回退 demo。
规则 2：后端 API 完全不存在 → 可显示「功能开发中」占位状态。
规则 3：任何「显示演示数据」操作 → 必须 Toast 明确提示「当前为演示数据」。
规则 4：Phase1 结束后，统一移除所有 demo fallback，替换为错误处理。
```
